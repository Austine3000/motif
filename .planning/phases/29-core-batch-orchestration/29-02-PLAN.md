Step 3b must implement the wave dispatch loop per the research (Example 3 in 29-RESEARCH.md):

**For each wave:**

1. **Report wave start:** "Starting wave {N}/{WAVE_COUNT}: {screen names}"

2. **Assemble context profile ONCE for all screens in the wave.** Read the same files as Step 2 (REQUIRED_FILES and OPTIONAL_FILES) but read them once — the orchestrator passes file paths to each Task(), not contents. Also run Step 2c (platform overlay resolution) and Step 2d (scaffold detection) once before the wave loop starts, storing HAS_OVERLAY, OVERLAY_PATH, STACK, and BROWNFIELD as variables.

3. **Spawn parallel Task() agents — ALL in a single message.** For each screen in the wave, spawn one Task() using the SAME agent_spawn template from Step 3, but with this ADDITIONAL block prepended to the Task prompt:

```
## BATCH MODE INSTRUCTIONS
You are composing in batch mode (wave {wave_index + 1} of {WAVE_COUNT}).

CRITICAL DIFFERENCES from single-screen mode:
1. After validation (compose-validator.js), do NOT run `git commit`. Leave validated files staged but NOT committed. The orchestrator will commit your work.
2. Do NOT modify tokens.css or COMPONENT-SPECS.md. If a token is missing, note it in SUMMARY.md under "## Missing Tokens" and use the closest existing alternative.
3. Your SUMMARY.md "## Files Created" section MUST list every file with its full path. The orchestrator uses this list to stage files for commit.
4. If compose-validator.js returns "fail": run `git reset HEAD [files]` to unstage. Write "Validation: FAILED" in SUMMARY.md. Do NOT delete files.
5. If compose-validator.js returns "pass" or "warn": leave files staged. Write "Validation: PASSED" (or "WARNED") in SUMMARY.md.
```

4. **Wait for all agents in the wave to complete.**

5. **Collect wave results.** For each screen in the wave:
   - Check if `.planning/design/screens/{SCREEN_NAME}-SUMMARY.md` exists
   - If exists: read ONLY the `## Validation` and `## Files Created` sections (targeted read, NOT full file)
   - Classify: PASSED (commit), WARNED (commit), FAILED (skip), CRASHED (no summary — skip)
   - Track results in an in-memory list: `{name, status, files[]}`

6. **Commit successful screens SEQUENTIALLY.** For each screen with PASSED or WARNED:
   - Parse file paths from "## Files Created" section of SUMMARY.md
   - Run `git add {file1} {file2} ...` with explicit file paths (NEVER `git add .` or `git add -A`)
   - Also stage the SUMMARY.md and ANALYSIS.md: `git add .planning/design/screens/{SCREEN_NAME}-SUMMARY.md .planning/design/screens/{SCREEN_NAME}-ANALYSIS.md`
   - Run `git commit -m "design(compose): implement {SCREEN_NAME} screen"`

7. **Update STATE.md atomically.** Build JSON payload:
   ```
   {"updates":[{"name":"login","status":"composed"},{"name":"dashboard","status":"composed"},{"name":"settings","status":"failed"}],"screens_composed":N,"phase":"COMPOSING"}
   ```
   Run: `node .claude/get-motif/scripts/motif-state.js batch-update-screens '{payload}'`
   Where screens_composed = total composed so far (previous + this wave's successes).

8. **Report wave results:** "Wave {N} complete: login (OK), dashboard (OK), settings (FAILED - {reason})"

**After all waves complete:**

9. **Batch summary.** Print a table:
   ```
   Batch complete: {succeeded}/{total} screens composed
   - login: OK (committed)
   - dashboard: OK (committed)
   - settings: FAILED (validation failure)
   ```

10. **Offer auto-run ONCE** (not per-screen). Use the same eligibility checks as Step 4b but offer only once after the full batch.
