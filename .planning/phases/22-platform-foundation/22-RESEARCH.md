# Phase 22: Platform Foundation - Research

**Researched:** 2026-03-09
**Domain:** Platform detection, CSS token transformation, framework registry
**Confidence:** HIGH

## Summary

Phase 22 establishes the foundation that all subsequent v1.4 phases depend on: a `platform` field in STATE.md, a deterministic token transformer script, pipeline integration that auto-generates platform-specific tokens after design system creation, and a framework registry mapping platform identifiers to their tooling details.

The scope is deliberately narrow -- no scaffolding, no composition changes, no auto-run. This phase produces infrastructure that Phases 23-26 consume. The token transformer is the highest-risk item: it must parse Motif's tokens.css format (CSS custom properties in `:root {}`) and emit TypeScript constant objects. The CSS format is well-structured and consistent (Motif controls the generation), making regex-based parsing reliable here. The framework registry is a static data file with no runtime logic -- it maps platform identifiers to commands and conventions.

**Primary recommendation:** Build the token transformer as a pure Node.js script (`scripts/token-transformer.js`) that reads tokens.css and emits `tokens.ts` (for React web) and `tokens.native.ts` (for React Native). Use the existing `motif-state.js update` command to persist the new `platform` field. Hook the transformer into `generate-system.md` as a post-generation step.

### Pattern 1: Deterministic Token Transformation (tokens.css -> tokens.ts)
**What:** A pure function that reads CSS custom properties from tokens.css and emits platform-specific TypeScript files. No LLM involvement. Deterministic: same input always produces same output.
**When to use:** After every `tokens.css` generation or regeneration.
**Example:**
```javascript
// scripts/token-transformer.js
// Source: Motif architecture -- CSS custom properties are the single source of truth

const CSS_VAR_PATTERN = /--([a-zA-Z0-9_-]+)\s*:\s*([^;]+);/g;

function parseTokensCSS(cssContent) {
  const tokens = {};
  let match;
  const regex = new RegExp(CSS_VAR_PATTERN.source, 'g');
  while ((match = regex.exec(cssContent)) !== null) {
    const name = match[1].trim();
    const value = match[2].trim();
    tokens[name] = value;
  }
  return tokens;
}

function categorizeTokens(tokens) {
  const categories = {
    colors: {},
    typography: {},
    spacing: {},
    radii: {},
    shadows: {},
    transitions: {},
    zIndex: {},
    icons: {},
    other: {},
  };

  for (const [name, value] of Object.entries(tokens)) {
    if (/^color-|^surface-|^text-|^border-/.test(name)) {
      categories.colors[name] = value;
    } else if (/^font-|^text-(?:xs|sm|base|lg|xl|2xl|3xl|4xl)|^leading-|^weight-/.test(name)) {
      categories.typography[name] = value;
    } else if (/^space-/.test(name)) {
      categories.spacing[name] = value;
    } else if (/^radius-/.test(name)) {
      categories.radii[name] = value;
    } else if (/^shadow-/.test(name)) {
      categories.shadows[name] = value;
    } else if (/^ease-|^duration-/.test(name)) {
      categories.transitions[name] = value;
    } else if (/^z-/.test(name)) {
      categories.zIndex[name] = value;
    } else if (/^icon-/.test(name)) {
      categories.icons[name] = value;
    } else {
      categories.other[name] = value;
    }
  }

  return categories;
}
```

### Anti-Patterns to Avoid
- **LLM-generating token files:** Never have the system architect agent produce tokens.ts or tokens.native.ts. The LLM generates tokens.css (its job). The transformer script produces derived formats (deterministic, no drift).
- **Platform-specific logic in init.md:** Keep init.md's new code minimal -- just ask the platform question and persist to STATE.md. All platform intelligence lives in the framework registry, not scattered across command files.
- **Hardcoding platform details in workflows:** Workflows should read from framework-registry.json, not embed platform-specific commands. This keeps the registry as the single source of truth for platform metadata.
- **Creating a separate state file for platform:** Use the existing STATE.md frontmatter. Adding `platform` to the existing state is one line via `motif-state.js update`. Do not create a new file.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| CSS parsing for tokens.css | Full CSS AST parser | Regex matching `--name: value;` | Motif controls the CSS format -- it is always `:root { --name: value; }`. A regex is sufficient and avoids dependencies. |
| YAML frontmatter for STATE.md | New YAML parser | Existing `motif-state.js` `update` command | Already handles key-value read/write with frontmatter preservation. |
| Design token format conversion | Style Dictionary pipeline | Custom ~80-line script | Zero-dependency constraint. The transformation is mechanical: parse CSS vars, convert units, emit TS constants. |
| Framework version detection | Manual version checks | Use `@latest` with official `create-*` CLIs | Official CLIs handle version resolution internally. |

**Key insight:** The token transformer is intentionally simple because Motif controls both the input format (tokens.css generated by system architect) and the output format (tokens.ts consumed by Motif-generated components). There are no third-party format compatibility concerns.

## Common Pitfalls

### Pitfall 1: Token Value Unit Conversion Errors
**What goes wrong:** CSS uses `rem`, `px`, and string values. TypeScript token files for React Native need unitless numbers (density-independent pixels). A naive converter strips the unit but does not multiply: `0.5rem` becomes `0.5` instead of `8`.
**Why it happens:** Multiple CSS unit systems with different base values.
**How to avoid:** Build an explicit unit conversion table into the transformer:
- `Xrem` -> `X * 16` (base font size)
- `Xpx` -> `X` (already numeric)
- `Xem` -> `X * 16` (treat as rem for token context)
- Color values (`#hex`, `rgb()`, `hsl()`) -> pass through as strings
- Bare numbers -> pass through
- String values (font families, cubic-bezier, shadows) -> pass through as strings
**Warning signs:** Spacing values that are fractional instead of multiples of 4. Font sizes under 1.

### Pitfall 2: Token Categorization Mismatch Between Parser and Generator
**What goes wrong:** The token transformer categorizes `--text-primary` as typography (because it starts with `text-`), but in Motif's token format `--text-primary` is a color (text color). The generated TypeScript file puts it in the wrong category.
**Why it happens:** Motif's naming convention uses `text-` prefix for both text colors (`--text-primary`, `--text-secondary`) and text sizes (`--text-xs`, `--text-base`).
**How to avoid:** Use Motif's actual token naming patterns from generate-system.md:
- `--text-primary`, `--text-secondary`, `--text-tertiary`, `--text-inverse`, `--text-link` are **colors**
- `--text-xs`, `--text-sm`, `--text-base`, `--text-lg`, `--text-xl`, `--text-2xl`, `--text-3xl`, `--text-4xl` are **typography** (font sizes)
- Distinguish by checking if the suffix is a size indicator (xs/sm/base/lg/xl/2xl/3xl/4xl) or a semantic name.
**Warning signs:** Color values appearing in the typography section of tokens.ts.

### Pitfall 3: Platform Field Not Persisting Across /clear
**What goes wrong:** User selects `web-nextjs` during init. After `/clear` (which resets Claude Code context), the platform field is gone because it was stored in-memory rather than in STATE.md.
**Why it happens:** Forgetting to persist via `motif-state.js update` or storing in a variable instead of the file.
**How to avoid:** Use `node scripts/motif-state.js update platform web-nextjs` immediately after user selection. Verify persistence by reading back: `node scripts/motif-state.js read`. The existing motif-state.js already handles persistence -- just use it.
**Warning signs:** Platform field missing from STATE.md frontmatter after init completes.

### Pitfall 4: Shadow Values Break Token Categorization
**What goes wrong:** CSS shadow values contain spaces, commas, and multiple values: `--shadow-md: 0 4px 6px -1px rgba(0,0,0,0.1), 0 2px 4px -2px rgba(0,0,0,0.1);`. The regex captures the full value correctly, but the TypeScript emitter struggles with the multi-value string.
**Why it happens:** Shadow values are the most complex CSS values in the token set. They contain commas (which could be mistaken for value separators) and parentheses.
**How to avoid:** For web tokens.ts, pass shadow values through as-is (they are CSS strings used in inline styles). For React Native tokens.native.ts, shadows must be decomposed into `shadowColor`, `shadowOffset`, `shadowOpacity`, `shadowRadius` (iOS) and `elevation` (Android). The transformer should emit shadow values as structured objects for native, not strings.
**Warning signs:** Shadow values truncated at first comma. Missing shadow properties in React Native output.

### Pitfall 5: Recover Command Ignores Platform Field
**What goes wrong:** User runs `/motif:init`, selects `mobile-expo`. State is written. Later, state gets corrupted. `motif-state.js recover` rebuilds state from artifacts but does not recover the `platform` field because it only looks at file existence, not STATE.md content.
**Why it happens:** The `recover` function infers phase, vertical, stack, and screens from project artifacts. Platform is not inferrable from artifacts (no platform-specific files exist until Phase 23+ scaffolds something).
**How to avoid:** During init, also write platform to PROJECT.md (alongside vertical and stack). The recover function already reads PROJECT.md for vertical and stack -- add platform detection from the same file.
**Warning signs:** Platform field is `undefined` after state recovery.

## Code Examples

### Token Transformer: CSS to TypeScript (Web)
```typescript
// scripts/token-transformer.js -- web output (tokens.ts)
// Source: Motif architecture design, verified against existing token-extractor.js patterns

function generateWebTS(categories, hash) {
  const lines = [
    '// Auto-generated from tokens.css by Motif. Do not edit manually.',
    `// Source hash: ${hash}`,
    '',
  ];

  for (const [category, tokens] of Object.entries(categories)) {
    if (Object.keys(tokens).length === 0) continue;
    const camelCategory = kebabToCamel(category);
    lines.push(`export const ${camelCategory} = {`);
    for (const [name, value] of Object.entries(tokens)) {
      // Strip category prefix from key (color-primary-500 -> primary500)
      const key = stripPrefix(name, category);
      const camelKey = kebabToCamel(key);
      lines.push(`  ${camelKey}: '${value}',`);
    }
    lines.push('} as const;');
    lines.push('');
  }

  lines.push('export const tokens = {');
  for (const category of Object.keys(categories)) {
    if (Object.keys(categories[category]).length === 0) continue;
    lines.push(`  ${kebabToCamel(category)},`);
  }
  lines.push('} as const;');
  lines.push('');
  lines.push('export type Tokens = typeof tokens;');

  return lines.join('\n');
}
```

### Token Transformer: CSS to React Native TypeScript
```typescript
// scripts/token-transformer.js -- native output (tokens.native.ts)
// Source: Motif architecture, RN StyleSheet.create patterns

function convertToNativeValue(value, tokenName) {
  // rem -> dp (multiply by 16)
  const remMatch = value.match(/^(-?\d+\.?\d*)rem$/);
  if (remMatch) return parseFloat(remMatch[1]) * 16;

  // px -> numeric
  const pxMatch = value.match(/^(-?\d+\.?\d*)px$/);
  if (pxMatch) return parseFloat(pxMatch[1]);

  // bare number
  if (/^-?\d+\.?\d*$/.test(value)) return parseFloat(value);

  // font family: strip fallbacks
  if (tokenName.startsWith('font-') && value.includes(',')) {
    const primary = value.split(',')[0].trim();
    return primary.replace(/['"]/g, '');
  }

  // colors, cubic-bezier, other strings: pass through
  return value;
}

function generateNativeTS(categories, hash) {
  const lines = [
    '// Auto-generated from tokens.css by Motif. Do not edit manually.',
    `// Source hash: ${hash}`,
    '// Values are density-independent pixels (dp) unless otherwise noted.',
    '',
  ];

  for (const [category, tokens] of Object.entries(categories)) {
    if (Object.keys(tokens).length === 0) continue;
    const camelCategory = kebabToCamel(category);
    lines.push(`export const ${camelCategory} = {`);
    for (const [name, value] of Object.entries(tokens)) {
      const key = stripPrefix(name, category);
      const camelKey = kebabToCamel(key);
      const nativeValue = convertToNativeValue(value, name);
      if (typeof nativeValue === 'number') {
        lines.push(`  ${camelKey}: ${nativeValue},`);
      } else {
        lines.push(`  ${camelKey}: '${nativeValue}',`);
      }
    }
    lines.push('} as const;');
    lines.push('');
  }

  // Convenience theme export
  lines.push('export const theme = {');
  for (const category of Object.keys(categories)) {
    if (Object.keys(categories[category]).length === 0) continue;
    lines.push(`  ${kebabToCamel(category)},`);
  }
  lines.push('} as const;');

  return lines.join('\n');
}
```

### Framework Registry Lookup
```javascript
// Reading registry in any workflow/script
const fs = require('node:fs');
const path = require('node:path');

function getFrameworkConfig(platform) {
  const registryPath = path.join(
    __dirname, '..', '.claude', 'get-motif', 'references', 'framework-registry.json'
  );
```

## Open Questions

1. **Should tokens.ts use `as const` satisfies pattern?**
   - What we know: `as const` gives literal types. `satisfies` (TS 4.9+) validates against an interface while preserving literal types.
   - What's unclear: Whether downstream Motif-generated components need the literal types or just `string | number`.
   - Recommendation: Use `as const` only. Simpler, works everywhere. `satisfies` adds no value since there is no shared token interface to validate against.

2. **Should the framework registry include version pinning?**
   - What we know: Prior research recommends `@latest` for create commands. Pitfall research suggests pinning for reliability.
   - What's unclear: Whether Motif should pin to tested versions or always use latest.
   - Recommendation: Use `@latest` in the registry. Version pinning is a Phase 23+ concern when scaffolding actually runs. The registry stores the command pattern, not a version contract.

3. **How should token-transformer handle dark mode tokens?**
   - What we know: Current tokens.css uses `:root {}` for light mode. Dark mode is not yet implemented in Motif.
   - What's unclear: Whether dark mode tokens will use `@media (prefers-color-scheme: dark)`, a `.dark` class, or separate `--dark-*` variables.
   - Recommendation: Build the transformer to handle only `:root {}` tokens for now. Dark mode token transformation is a v1.5+ concern. The regex-based parser naturally ignores non-`:root` blocks.
