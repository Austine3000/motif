<task type="auto" id="25-01-01" wave="1" depends_on="25-W0-01">

  <action>
Create `.claude/get-motif/scripts/runtime-launcher.js` as the reusable Phase 25 auto-run entry point.

The launcher must:
- accept flags sufficient for post-compose use such as `--platform`, `--project-root`, `--project-name`, `--source compose`, and an opt-out/dry-run mode for verification
- read `.claude/get-motif/references/framework-registry.json`
- resolve the selected platform entry and fail clearly for unsupported or non-runnable platforms
- support two execution modes from registry metadata:
  - daemon/dev-server mode for Next.js and Vite
  - static-preview mode for `web-static`, where the launcher opens a file target directly without pretending to manage a background server
- spawn daemon runtimes without blocking the compose terminal
- parse stdout/stderr incrementally using platform-specific ready matchers from the registry
- extract the final preview URL from runtime output when the framework prints a different port than the default
- open the preview only after readiness succeeds, using native OS commands only (`open`, `xdg-open`, `cmd /c start ""`)
- expose a dry-run or explain mode so the Wave 0 harness can validate opener/command construction without launching a real browser

Update `framework-registry.json` so runnable platforms contain enough declarative runtime data for the launcher. Expand the contract for `web-nextjs`, `web-vite`, and `web-static` to include fields such as:
- execution mode (`daemon` vs `static-preview`)
- launch command/args
- working-directory policy
- `readyMatchers` array rather than a single loose string
- URL capture pattern or explicit default URL
- open strategy and preview target metadata

Keep the registry declarative and future-friendly. It is acceptable to add an Expo-shaped metadata surface for Phase 26, but this plan should only claim end-to-end support for Next.js, Vite, and static.
  </action>
